# genai-bench 单人版 · 手把手压测教学

> 这篇是给「第一次用这个页面」的人看的。全程用**我自己笔记本上的三个小模型**真实跑出来的数据，
> 每一步都配了截图（图上带编号和说明），照着做一遍就能明白「压测到底在测什么」。

---

## 0. 一句话先说清楚：压测不是"能不能通"

「能通」只说明服务活着。压测要回答的是另一件事：

> **加压到一定程度，延迟会不会突然翻脸？**

所以真正有用的输出是一张**拐点图**：横轴加压力，纵轴看延迟。这次我们真的压出来了 ——
Chat 从 1 个并发加到 8 个并发，吞吐只从 47 涨到 72（几乎涨不动了），
**P99 却从 10 秒飙到 65 秒**。那个开始往上翘的点，就是这台机器的天花板。

## 2. 页面地图：整页只有一条主线

![认识「新建实验」](demo/01_overview.png)

从上往下就五步：**探活 → 选任务 → 填连接 → 挑套餐/改参数 → 发起**。

* **①探活**：只发一次极小的 `/v1/models` 请求，专门用来排除"网络不通 / Key 错 / 模型名不存在"。
* **②参数反显**：把历史实验、本地预设、或粘贴来的 CLI 命令还原成完整表单（连折叠项和固定值都还原）。
* **③选择任务**：**单选** —— 一次只压一个任务。两个压力同时跑，两条延迟曲线会互相污染，谁都读不出来。
* **④本地 Tokenizer**：上传一次，之后离线可用，不需要 HF_TOKEN、不需要联网。

再往下半页是套餐和发起：

![套餐 / 参数扫描 / 发起](demo/02_presets.png)

**7 个套餐**全部按"你想干什么"命名，不是按参数命名：

| 套餐 | 什么时候选它 |
|---|---|
| 🔵 **帮我找出能扛多少**（默认推荐） | 不知道设多少并发/批大小，想一次看全 |
| ⏱ 找延迟拐点 | 在线服务，对延迟敏感 |
| 🚀 找最大吞吐 | 离线批处理，只要吞吐 |
| 🎯 标准施压 | 只想快速验一次 |
| 🔥 长时间烤机 | 上线前确认稳定性 |
| 📚 长上下文压测 | 业务里有长文档/长对话 |
| 💥 极限施压 | 主动找上限、压出失败点 |

**套餐只是"把参考值填进表单"，不会自动开跑**，也不会缩短你设的时长 —— 填完你还能改每一个数。

## 3. 第一次动手：Chat

### 3.1 选任务、填连接

![选 Chat 并填连接](demo/04_chat_connection.png)

两个坑，图上都标了：

1. **`api_base` 不要带 `/v1`**。引擎自己会拼 `/v1/chat/completions`，你写成 `…:8101/v1`
   就变成 `/v1/v1/…`，直接 404。（这条我专门在后端做了归一化，但你最好也别写。）
2. **Tokenizer 填本地目录**：`C:\UGit\genai-bench\tools\local_models\chat`，完全离线。

API Key 随便填一个（比如 `sk-local-demo`）：本地服务不校验，但引擎的 openai 后端**必须**有这个值，
否则 click 直接 `exit 2`。它只会走**子进程环境变量**，不会进命令行、不会写进 `params.json`、不会进导出包。

### 3.2 先探活

![探活](demo/05_preflight.png)

探活失败会明确告诉你差在哪一层：连不上 / 401 / 模型名不存在。

### 3.3 三个旋钮

![Chat 参数](demo/06_chat_params.png)

| 缩写 | 含义 | 大白话 |
|---|---|---|
| **L** | 对话长度 | 每次问它多长 |
| **c** | 并发 | 几个"人"同时问 |
| **t** | 时长 | 压多久 |

> 图里为了在 CPU 上快速出结果，用了 `100 / 8 / 2min`。
> **正式测请用模板默认的 `1k / 32 / 10min`** —— 默认档就是"施压档"，目的就是压出拐点。

### 3.4 确认参数，再发起

![预览最终参数](demo/07_preview_chat.png)

「预览最终参数」显示的是**真正要提交给后端的那份表单值**（全程不含 API Key）。
确认没问题再点「发起实验（串行）」。

### 3.5 发起后会自动跳到实时监控

![实时监控](demo/08_live_monitor.png)

这一页是**只读**的：所有数字都是引擎已经算好、写进结果文件的，页面只读不改算 ——
所以你在这里看到的 P99，和导出 JSON 里的完全一致。

注意 8 并发的样子：**P50 8.4 秒、P99 72 秒**。P50 还算能忍，P99 已经是"用户要骂人"的级别了。
这就是单机跑 0.5B 模型的真实体感。

### 3.6 队列：永远一次只跑一个

![串行队列](demo/09_queue.png)

单选、整串套餐、参数扫描、批量重跑 —— **全部进同一条队列**。
想打断就点那一行的「停止」：它会连正在跑的 locust 子进程一起收掉，并把还没开跑的兄弟档位标成
`stopped`，**不会**自动接着跑下一档。

## 4. 关键一步：并发扫描，把拐点压出来

要压出拐点，就得**同一个任务、只改一个维度、跑好几个档位**。发起区最下面就是干这个的：

![参数扫描 / 标题 / 发起](demo/03_launch.png)

* **④参数扫描**：勾上「启用扫描」，选一个字段（并发 / 批大小 / 对话长度），
  把档位列表填成 `1,4,8`（逗号分隔，可随意改）。整串套餐会自动把档位填进这里。
* **⑤标题**：留空会按模板自动生成（如 `Chat · chat · c32 L1k t10m · 1107-1430`）。
  它只是**展示用的装饰**，改标题不会改 `run_id`、不会改目录名、不会断 Dashboard 链接。
* 点「发起实验（串行）」后，这几档会**一次性进同一条队列**，一档一档跑，跑完自动成组。

这次我把 Chat 的并发跑成 `1 → 4 → 8`，然后到历史页勾选这 3 条，点「并排对比图」：

![拐点图](demo/15_chart.png)

**这张图就是压测的全部意义：**

| 并发 | 吞吐 | P50 | **P99** |
|---|---|---|---|
| 1 | 47.1 tok/s | 1.38 s | **10.09 s** |
| 4 | 66.8 tok/s | 4.16 s | **34.23 s** |
| 8 | 72.3 tok/s | 8.45 s | **65.46 s** |

* 并发 1→8，吞吐只涨了 **1.5 倍**（47→72），已经**涨不动**了；
* 同一区间 P99 却涨了 **6.5 倍**（10→65）。

**结论：这台机器的 Chat 合理并发上限在 4 附近；再往上加，加的不是能力，是排队。**

## 5. Embedding：压力是"批大小 × 文档长度 × 并发"

![Embedding 参数](demo/10_embedding_params.png)

Embedding 和 Chat 不一样：**一次请求带一批文档**，所以压力有三个来源。

> **并发以前是写死 1 的**（上游为了对照实验强制 `num_concurrency=[1]`）。
> 现在已经真正放开：批 10 × 并发 10 和 批 2 × 并发 50，**总在飞文档数都是 100**，
> 压力相同、切分不同，正好用来对比"显存/调度更吃哪种"。
> 图表横轴可以直接选「总在飞文档数(批×并发)」，两条就落在同一个 x 上了。

![预览 Embedding](demo/11_preview_embedding.png)

这次的结果：`批32 / 文档256 / 并发2` → **1.75 req/s，P50 1.09 s，P99 1.20 s，错误率 0**。
（注意这是**一个请求处理 32 篇文档**的耗时，折到单篇约 37 ms。）

## 7. 回看、导出、复现

![历史结果](demo/14_history.png)

* **原始结果原样保留**：引擎产出的文件名和内容一个字都不改，就放在实验目录里。
* **批量下载 ZIP**：勾多条 → 一个包，里面有
  `README.txt`、`summary.csv`、`compare_p99.png`，以及每条实验一个可读目录（`results/` 原始结果原名、
  `params.json` 脱敏参数、`meta.json`、`note.txt`、`charts/*.png`）。
* **跨页勾选**会保留；「全选（当前筛选全部）」导出的条数和筛选结果一致。
* **以此为模板**：把这条实验的完整参数（含折叠项、固定值）填回表单，改一个数再跑 ——
  这是复现和对比最快的方式，和「重跑」不是一回事（重跑是原样再来一次）。

我验证过：导出的 ZIP 里搜不到 `sk-local-demo`，也搜不到 `MODEL_API_KEY`。

## 8. 五个最容易踩的坑

1. **`api_base` 带了 `/v1`** → 变成 `/v1/v1/chat/completions`，404。
2. **不填 API Key** → 引擎 `exit 2`（`Invalid value for '--api-key': API key is required`）。
   排查时看实验目录的 `meta.json` 里的 `error`，子进程的输出是被吞掉的。
3. **两个压力同时跑** → 指标互相污染。所以这里强制串行。
4. **等不及把时长调成 0** → 时长只有 2 / 10 / 30 分钟，且**不要靠缩短时长压出拐点**；
   时长不够，稳态还没建立就结束了。急的话先用 2 分钟看趋势，正式测还是 10 分钟。
5. **批大小 × 并发开太大** → CPU/显存直接 OOM。Embedding 想加大压力，优先加批大小和文档长度。

## 9. 这次真跑出来的两个 bug（顺手修了）

写这篇教程时页面有两个真问题，都修了并补了回归测试：

1. **发起后没有跳到实时监控**。
   `GB.go('/#/dashboard/x')` 给 `location.hash` 赋值时浏览器又加了一个 `#`，hash 变成 `#/#/dashboard/x`，
   路由解析出 `view === "#"`，静默回落到「新建实验」页。现在 `GB.go` 会把 `#`、`/#` 统一归一化。
2. **多条批量下载 ZIP 直接 500**。
   导出文件名是 `genai-bench_3条_….zip`，HTTP 头只允许 latin-1，gevent 抛
   `UnicodeError: Non-latin1 header`。现在按 RFC 6266/5987 发两个参数：
   ASCII 回退 `filename="genai-bench_3_….zip"` + `filename*=UTF-8''…`（中文名不丢）。

另外修了个小的：流式响应的 `completion_tokens` 之前把 prompt 长度也算进去了，会把吞吐算虚高。
